## 1. 项目概述

### 1.1 背景

面向昇腾 NPU 的大模型推理部署，当前主要矛盾是：**模型结构复杂（MoE 稀疏专家 + MLA 压缩注意力 + 长序列），而通用算子库对特定 shape / dtype / 数据布局的覆盖不完整，导致部分算子成为端到端性能瓶颈。**

本方案建立一条从「部署 → 基线 → 采集 → 分析 → 算子开发 → 验证」的完整闭环流水线，把性能优化从"凭经验调参"变成"由 profiling 数据驱动的定向算子开发"。

### 1.2 目标

| 层次 | 目标 | 度量 |
|------|------|------|
| 流程目标 | 建立可复用的性能优化流水线 | 新模型接入可在 N 天内完成全流程 |
| 算子目标 | 识别并优化 Top-N 热点算子 | 单算子相对标杆加速比 ≥ 1.2× |
| 模型目标 | 端到端推理性能提升 | TPOT 降低 ≥ 5%，或吞吐提升 ≥ 5% |
| 质量目标 | 优化不引入精度损失 | 评测集分数下降 < 0.5%，输出余弦相似度 > 0.99 |

> 上述数值为**验收门槛建议值**，需在阶段二基线数据出来后与业务方共同校准。

### 1.3 核心原则

1. **数据驱动**：任何算子改动前必须有 profiling 数据支撑，禁止"我认为它慢"。
2. **先测量后优化**：基线不建立，优化无法归因。
3. **单变量原则**：实验矩阵中每次只变更一个变量（配置/代码），否则结果无法解释。
4. **精度红线**：性能优化不得改变计算语义，精度异常一律视为硬失败。
5. **可复现**：每次实验记录 代码 commit + 完整配置 + 环境快照 + 结果，三者缺一不可。
6. **产物归仓**：除模型部署外，阶段二 ~ 六的全部产物必须落在本仓库目录内（见 2.4）；写在仓库外的结果视为流程违规，不予采信。

## 4. 阶段一：模型部署（vLLM-Ascend）

### 4.1 目标

得到**配置固化、可重复启动、可对外服务**的推理端点，作为后续所有基线与 profiling 的载体。

### 4.2 关键活动

- **环境准备** —— 独立虚拟环境（不同 vLLM 版本对环境要求冲突，必须隔离）；CANN / ATB 环境变量；torch_npu、vLLM、vLLM-Ascend 三者**版本严格配套**。
- **权重准备** —— 确认 GLM / DeepSeek 权重实际路径与显存可行性估算；DeepSeek 级模型（671B）超单机显存，**必须走 W8A8 量化 + EP**。
- **分层推进** —— 冒烟层（Qwen3.5-0.8B 单卡，验证环境正确性，定位成本最低）→ 验证层（中等规模模型，验证多卡并行与量化路径）→ 目标层（GLM / DeepSeek 正式模型）。
- **配置固化** —— 环境变量与启动参数落成可复现脚本；调试期用的 `ASCEND_LAUNCH_BLOCKING` 之类开关，调通后必须关闭（严重影响性能）。

### 4.3 交付物

```

  env-<模型>.sh          # 环境变量固化脚本（快照）
  serve-<模型>.sh        # 启动脚本（含完整参数）
logs/
  deploy-smoke-<日期>.log
```

> 本阶段**在仓库外执行**（权重与服务启动脚本位于外部路径），本仓库只归档配置快照，用于保证基线数据可追溯 —— 快照与 `results/` 中的 `exp_id` 一一对应。

### 4.4 门禁 G1

服务稳定提供 OpenAI 兼容接口；连续 100 次请求无错误；服务重启后可复现。

## 5. 阶段二：基线数据采集

### 5.1 目标

建立**可比对的性能坐标系**。后续任何优化的收益，都以本阶段数据为分母。

### 5.2 关键活动

- **确定指标体系** —— 核心为 TTFT、TPOT/ITL、吞吐、QPS、显存占用与 P50/P90/P99 分位。**TTFT 与 TPOT 存在权衡，报告必须成对给出**，单看一个指标会误导。
- **设计测试矩阵（单变量原则）** —— 固定模型、并行配置、量化方式、硬件、环境变量、commit；变化输入长度 ISL、输出长度 OSL、并发数、场景（纯 Prefill / 纯 Decode / 混合）。资源有限时先跑少数几个高价值基准点。
- **选择采集工具** —— vLLM 内置 benchmark / 昇腾官方 ais_bench（交叉验证）/ 复用已有脚本改造。三者可互相校验。
- **遵守采集纪律** —— 先预热再统计（规避 DVFS 调频与 JIT 开销）；只测稳态不测冷启动；每点重复 ≥ 3 次并给出方差，方差 > 5% 视为无效；锁定 CPU 调频与 swap；记录温度；禁止并发实验。
- **规范化记录** —— 每条基线记录字段固定（模型、权重路径、量化方式、框架版本、commit、并行配置、完整启动参数、环境变量、指标分位数、备注），保证任意两条记录可比对。

### 5.3 交付物

```
results/baseline/
  baseline-<模型>-<日期>.json       # 结构化数据（字段规范见阶段文档）
  baseline-<模型>-<日期>.md         # 可读报告（表格 + 结论）
bench/
  run_baseline.sh                   # 一键跑完整矩阵
  parse_results.py                  # 结果汇总
```

> 基线一经确认即**冻结**，后续优化对比一律引用该 `exp_id`。

全测试矩阵跑完，性能方差 < 5%；不通过则排查环境干扰（温度 / 降频 / 邻居任务）。

## 6. 阶段三：算子 Profiling 采集

### 6.1 目标

把端到端耗时**分解到算子粒度**，得到"哪些算子在吃时间"的量化事实。

### 6.2 关键活动

- **三层采集粒度，自顶向下** —— L1 模型级（profiler，端到端时间都去哪了）→ L2 算子级（msprof，算子内部瓶颈在哪条流水线）→ L3 微基准（单算子独立压测，该 shape 下的算力/带宽利用率）。先用 L1 定位热点，再按需下钻，不要一上来就做 L3。
- **控制采集窗口** —— 采集区间**只包含要分析的请求**，且必须跳过 warmup（图捕获/JIT 编译开销极高，会严重污染占比）。
- **Prefill / Decode 分开采集** —— 两者 kernel 构成完全不同，混采会导致占比失真。
- **多卡场景** —— 指定 device 或只采 rank 0，避免所有 rank 同时采集造成数据量爆炸。
- **遵守采集纪律** —— profiling 有 10% ~ 3× 的运行时开销，**只能用于占比分析，绝不能把 profiling 耗时当作 TTFT/TPOT 性能数据**；限制 active 步数，避免产出 GB 级 json 无法分析。

### 6.3 交付物

```
profiles/
  <模型>/<日期>-prefill/        # prefill 场景采集
    ASCEND_PROFILER_OUTPUT/kernel_details.csv
  <模型>/<日期>-decode/         # decode 场景采集
  <模型>/<日期>-<配置>/          # 每变更一个关键配置采一次
tools/
  profile_run.sh                # 采集封装
  profile_summary.py            # 汇总：Top-K 算子 + 占比
```

## 7. 阶段四：算子分析

### 7.1 目标

从 profiling 原始数据中提炼出**可执行的优化决策清单**：哪些算子该动、怎么动、优先级如何。

### 7.2 关键活动

**对每个热点算子，依次回答三个问题：**

- **Q1 耗时是否正常？** —— 四类判据交叉验证：
  - 理论下限对比（Memory-bound 算子的访存量 ÷ 实测带宽；Compute-bound 算子的 FLOPs ÷ 实测算力；效率 = 理论 ÷ 实测，明显偏低即说明有优化空间。注意小 shape 下启动开销占比高，达不到峰值属正常，需按 shape 规模分级判断）
  - pipe 占比分析（mte2 / mte3 / vec / cube / fixpipe / scalar / mte1，比重异常指向不同根因）
  - 横向对比（同族算子在不同 shape 下的 scaling 曲线是否平滑；与 CANN 内置实现、sglang 实现对比）
  - 经验阈值快速筛查（大量极小 kernel、耗时波动过大、prefill/decode 占比差异等）
- **Q2 异常原因是什么？** —— 归入典型异常模式：小算子碎片化、格式转换开销（`TransData`/`ND2NZ`）、搬运占比过高、流水未打满（Double Buffer 未生效）、tiling 尾块浪费、scalar 拖累、同步等待、未走图模式。每种模式对应不同的优化方向。
- **Q3 可融合吗？** —— 按数据依赖（生产者-消费者且中间结果只有一个消费者，必要条件）、中间结果落盘代价、逐元素性质、形状兼容、类型兼容综合判定，并用收益模型估算：

  ```
  融合收益 ≈ 节省的 HBM 读写量 / HBM带宽
           = (中间张量元素数 × dtype字节 × 2) / 带宽     # ×2 = 省一次写 + 一次读
  ```

  收益必须大于融合后 kernel 的额外开销，否则不划算。

**先查后造（顺序不能反）：**

1. 图模式是否已自动融合？—— 开启 ACLGraph 后重采 profiling，对比算子数量。
2. CANN 融合算子库是否已有？—— 查 `torch_npu` 的 `npu_*` 融合接口，已有则直接替换。
3. sglang / 其他框架是否已有实现？—— `/home/zhujianwei/sglang` 中可能已有可参考 kernel。
4. 以上都没有 → **才进入阶段五自研**。

> 自研融合算子的成本远高于替换为已有接口，**前 3 步能解决 80% 的问题**。

**优先级排序：**

```
优先级 = (耗时占比 × 预期收益系数) / 实施难度系数
收益系数：融合 0.6~0.9 / 替换已有接口 0.9 / 算法重写 0.5
难度系数：替换已有接口 1 / 简单逐元素融合 2 / 复杂融合 4 / 算法重写 6
```

落在「高占比 + 易实施 → 立即做」、低占比 + 难实施 → 不做」的决策矩阵中。

### 7.3 交付物：算子画像表（核心交付）

`analysis/op_profile-<模型>-<日期>.csv`，字段至少包含：

| 字段 | 含义 |
|------|------|
| `op_name` / `op_type` | 算子名 / 类型 |
| `total_time_ms` / `time_ratio` | 总耗时 / 耗时占比 |
| `call_count` / `avg_time_us` | 调用次数 / 平均单次耗时 |
| `stage` | prefill / decode / both |
| `pipe_dominant` | 主导 pipe |
| `theorem_time_us` / `efficiency` | 理论下限耗时 / 计算效率 |
| `bottleneck` | 瓶颈类型 |
| `verdict` | **正常 / 异常 / 可融合 / 待定** |
| `fusion_candidate` | 建议融合目标 |
| `priority` / `action` | 优先级评分 / 处置建议 |

### 7.4 门禁 G4

Top-20 耗时算子全部有明确 `verdict` 与 `action`，**无"待定"**；不通过则补充采集或补充分析。

## 8. 阶段五：CANNBot 算子开发

### 8.1 目标

把阶段四产出的决策清单落地为**精度达标、性能达标的算子实现**，并具备上生产的形态。

### 8.2 关键活动

- **能力选型** —— 按任务从 2.4 的 CANNBot 插件清单中选型（性能采集、直调/注册开发、tiling 设计、精度调试、性能专项优化、端到端编排）。
- **开发路径分流** —— 单算子性能差（efficiency 低）→ 调优已有实现；多个逐元素算子需合并 → 新建融合 kernel；算子完全缺失 → 从零实现。三条路径工具链不同。
- **标准六步，顺序不可颠倒** —— 需求描述 → 环境检查 → 方案设计（tiling + 流水）→ 代码实现 → 精度验证 → 性能调优。

  > **精度未通过就调性能，等于在错误的实现上做优化。**

- **交付形态** —— 直调（Direct Invoke，编译快、调试易，开发迭代阶段用）→ 验证通过 → 转注册（Registry Invoke，可被框架/图调用，上生产用）。
- **性能抓手**（速查要点）—— 减少 GM 往返是第一优先级（融合的本质就是把中间结果留在 UB）；Double Buffer 必须显式开启（`TQue` depth ≥ 2）；Tiling 匹配 UB 容量并兼顾多核负载均衡；减小 scalar 开销（地址计算移出内层循环）；对齐访问；dtype 选择；同步最小化；合理核间切分。
- **融合算子特别提示** —— 融合后 UB 占用叠加，需重新核算 tiling（这是融合最常见的失败原因）；融合链通常 **2~4 个算子一段**收益最佳，过长反而劣化；注意 dtype 转换点变化带来的精度累积误差。

### 8.3 交付物

```
ops/<算子名>/
  README.md              # 算子说明、数学定义、接口、性能数据
  src/                   # AscendC kernel + tiling 实现
  host/                  # host 侧封装
  test/                  # 精度测试（对比 golden）+ 性能测试
  build.sh               # 一键编译
  docs/design.md         # 设计方案（tiling 策略、流水图）
  docs/perf.md           # 性能数据与优化轮次记录
analysis/perf-rounds.md  # 性能优化轮次记录：每轮改了什么、pipe 占比变化、耗时变化
```

**精度标准（建议）**

| dtype | 判定 | 阈值 |
|-------|------|------|
| fp16 / bf16 | 相对误差 `\|a-b\|/(\|a\|+ε)` | < 1e-3 |
| fp32 | 相对误差 | < 1e-4 |
| int8 量化 | 与浮点 golden 的相对误差 | < 1e-2 |

**性能标准**：单算子相对标杆加速比 ≥ 1.2×，或计算效率 ≥ 60% 理论峰值。

## 9. 阶段六：测试验证

### 9.1 目标

证明优化**既有效、又无损**，且收益在端到端可观测 —— 而不只是在单算子微基准上好看。

### 9.2 关键活动

**三层验证体系，逐层通过后才进入下一层：**

- **L1 算子级** —— 精度：与参考实现（numpy/torch CPU）逐元素对比，覆盖边界 shape（1、质数长度、极大值、极小值）；性能：与标杆对比取加速比；稳定性：重复采集多次，耗时方差 < 5%（方差过大说明实现依赖了不确定的调度）。
- **L2 模型级** —— 数值一致性：在模型中间层 dump tensor，与未优化版本逐层对比余弦相似度与相对误差（融合/替换算子的**关键验证**）；端到端精度：跑评测集，分数下降超阈值视为不通过；端到端性能：复用阶段二的测试矩阵与脚本，与基线**逐点对比**。
- **L3 回归与异常场景** —— 全测试矩阵重跑并与基线逐点对比；必须覆盖异常场景：超长序列（`max_model_len` 边界）、恰好边界 shape（tiling 整除数 ±1）、并发数突变（图模式分档覆盖）、空输入/单 token、连续运行 ≥ 1 小时（显存泄漏与精度漂移）。
- **回滚预案** —— 每个优化以独立 commit 提交，通过 feature flag 可关闭，出问题时能快速回滚。

### 9.3 交付物

```
verify/
  op_accuracy_<算子>.md       # 算子精度报告
  op_performance_<算子>.json  # 算子性能对比
  model_accuracy.md           # 模型评测集结果
  e2e_compare.md              # 端到端对比（基线 vs 优化后）
  regression.md               # 回归测试报告
```
