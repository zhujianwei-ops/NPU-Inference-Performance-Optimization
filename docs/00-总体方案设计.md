# vLLM-Ascend 大模型推理性能优化总体方案

> 版本：v0.1（设计稿）
> 日期：2026-09-15
> 适用平台：Ascend 910 系列 / CANN 9.0.0 / vLLM-Ascend
> 优化对象：GLM 系列、DeepSeek 系列（MoE + MLA/GQA 大模型）

---

## 1. 项目概述

### 1.1 背景

面向昇腾 NPU 的大模型推理部署，当前主要矛盾是：**模型结构复杂（MoE 稀疏专家 + MLA 压缩注意力 + 长序列），而通用算子库对特定 shape / dtype / 数据布局的覆盖不完整，导致部分算子成为端到端性能瓶颈。**

本方案建立一条从「部署 → 基线 → 采集 → 分析 → 算子开发 → 验证」的完整闭环流水线，把性能优化从"凭经验调参"变成"由 profiling 数据驱动的定向算子开发"。

### 1.2 目标

| 层次 | 目标 | 度量 |
|------|------|------|
| 流程目标 | 建立可复用的性能优化流水线 | 新模型接入可在 N 天内完成全流程 |
| 算子目标 | 识别并优化 Top-N 热点算子 | 单算子相对标杆加速比 ≥ 1.2× |
| 模型目标 | 端到端推理性能提升 | TPOT 降低 ≥ 5%，或吞吐提升 ≥ 5% |
| 质量目标 | 优化不引入精度损失 | 评测集分数下降 < 0.5%，输出余弦相似度 > 0.99 |

> 上述数值为**验收门槛建议值**，需在阶段二基线数据出来后与业务方共同校准。

### 1.3 核心原则

1. **数据驱动**：任何算子改动前必须有 profiling 数据支撑，禁止"我认为它慢"。
2. **先测量后优化**：基线不建立，优化无法归因。
3. **单变量原则**：实验矩阵中每次只变更一个变量（配置/代码），否则结果无法解释。
4. **精度红线**：性能优化不得改变计算语义，精度异常一律视为硬失败。
5. **可复现**：每次实验记录 代码 commit + 完整配置 + 环境快照 + 结果，三者缺一不可。
6. **产物归仓**：除模型部署外，阶段二 ~ 六的全部产物必须落在本仓库目录内（见 2.4）；写在仓库外的结果视为流程违规，不予采信。

### 4.3 权重准备

| 模型 | 权重来源 | 显存估算（bf16） | 建议并行策略 |
|------|----------|------------------|--------------|
| GLM 系列（含 Flash 版本） | 待确认本地路径 | 参数量 × 2 B | TP=8/16 |
| DeepSeek 系列（V3/R1 级） | 待确认本地路径 | 671B × 2 B ≈ 1.3 TB（超单机） | **必须 W8A8 量化 + EP** |
| Qwen3.5-0.8B | `/home/public/models/Qwen3.5-0.8B` | < 2 GB | 单卡，**用于流程冒烟** |

**显存需求公式**（用于判断配置是否可行）：

```
权重显存 = 参数量 × 每参数字节   (bf16=2, W8A8≈1.06)
KV Cache = 2 × layers × kv_heads × head_dim × dtype_bytes × 序列长度 × 并发数
总需求   = (权重 + KV) / tp_size  ≤  单die_HBM × 卡数 × gpu_memory_utilization
```

**量化路径**：DeepSeek 级模型必须走 W8A8。参考 `/home/zhujianwei/modelslim-fix`，产出量化权重后由 vLLM-Ascend 加载。

### 4.4 部署配置要点

```bash
export HCCL_SOCKET_IFNAME=<实际网卡>        # 多卡通信必须，用 ip addr 确认
export GLOO_SOCKET_IFNAME=<实际网卡>
export PYTORCH_NPU_ALLOC_CONF=expandable_segments:True
export ASCEND_USE_FIA=1                     # 使用 FIA 加速注意力
export VLLM_USE_V1=1                        # vLLM V1 引擎
export TASK_QUEUE_ENABLE=2                  # 算子下发队列优化
export HCCL_OP_EXPANSION_MODE=AIV
# 首次调试加 ASCEND_LAUNCH_BLOCKING=1 定位报错，调通后必须 unset（严重影响性能）
```

**核心启动参数决策表：**

| 参数 | 作用 | 建议 |
|------|------|------|
| `--tensor-parallel-size` | 张量并行 | A3 单机 16 die 可用 TP=16；A2 建议 TP=8 跨机 |
| `--enable-expert-parallel` | MoE 专家并行 | **MoE 模型必开**，与 DP 组合提升吞吐 |
| `--max-model-len` | 最大序列长度 | 按业务实际设定，过大会浪费 KV 显存 |
| `--max-num-seqs` | 最大并发批 | 吞吐/延迟的主要权衡旋钮 |
| `--max-num-batched-tokens` | 单批最大 token 数 | chunked prefill 的切分粒度 |
| `--gpu-memory-utilization` | 显存水位 | 0.9 起步，OOM 则下调 |
| `--enable-chunked-prefill` | 分块预填充 | 长序列 + 高并发**必开** |
| `--enable-prefix-caching` | 前缀缓存 | 多轮对话场景收益显著 |
| `--quantization ascend` | 昇腾量化 | W8A8 权重加载 |
| `--enforce-eager` | 关闭图模式 | **仅调试用**，生产必须开图模式 |
| `--compilation-config` | ACLGraph 配置 | 生产开启，注意 batch size 分档覆盖 |
| `--speculative-config` | 投机解码 | MTP/EAGLE，decode 瓶颈时可考虑 |

**分层部署策略（强烈建议）：**

1. **冒烟层**：用 Qwen3.5-0.8B 单卡跑通全流程，验证环境正确性 —— 出问题定位成本最低。
2. **验证层**：中等规模模型（如已有 Qwen3-27B 级），验证多卡并行与量化路径。
3. **目标层**：GLM / DeepSeek 正式模型。

## 5. 阶段二：模型基线数据采集

### 5.1 目标

建立**可比对的性能坐标系**。后续任何优化的收益，都以本阶段数据为分母。

### 5.2 指标体系

| 指标 | 定义 | 主导阶段 | 采集方式 |
|------|------|----------|----------|
| **TTFT** | Time To First Token，首 token 延迟 | Prefill | 流式请求，记录首 chunk 时间 |
| **TPOT / ITL** | Time Per Output Token，平均出字间隔 | Decode | (总耗时 - TTFT) / (输出长度 - 1) |
| **吞吐** | output tokens/s、total tokens/s | 综合 | 固定并发下稳态统计 |
| **QPS** | 每秒完成请求数 | 综合 | 固定时长压测 |
| **显存占用** | 权重的 / KV 的 / 峰值 | — | `npu-smi info` + 内部日志 |
| **稳定性** | P50 / P90 / P99 分位 | — | 多次重复取分位 |

> **注意**：TTFT 与 TPOT 存在权衡（batch 越大 TPOT 越差、吞吐越好）。报告必须**成对给出**，单看一个指标会误导。

### 5.3 测试矩阵（单变量原则）

**固定变量**：模型、并行配置、量化方式、硬件、环境变量、commit。

| 维度 | 取值 | 说明 |
|------|------|------|
| 输入长度 ISL | 128 / 1K / 4K / 8K / 16K / 32K | 覆盖短查询到长文档 |
| 输出长度 OSL | 128 / 512 / 1K | OSL 短则 decode 占比低 |
| 并发 | 1 / 4 / 8 / 16 / 32 / 64 / 128 | 找吞吐拐点与延迟悬崖 |
| 场景 | 纯 Prefill / 纯 Decode / 混合 | 分离瓶颈定位 |

**优先采集的 8 个基准点**（资源有限时先跑这些）：

| 编号 | ISL | OSL | 并发 | 场景标签 |
|------|-----|-----|------|----------|
| B1 | 128 | 128 | 1 | 低延迟基线 |
| B2 | 1K | 128 | 1 | 单请求对话 |
| B3 | 1K | 1K | 16 | 典型服务 |
| B4 | 4K | 512 | 16 | 中等上下文 |
| B5 | 8K | 128 | 32 | 长上下文高并发 |
| B6 | 16K | 128 | 32 | 长上下文 |
| B7 | 32K | 128 | 8 | 超长上下文 |
| B8 | 1K | 1K | 64 | 吞吐峰值 |

### 5.4 采集方法

**方案 A：vLLM 内置 benchmark（推荐起步）**

```bash
python -m vllm.entrypoints.openai.api_server \
    --model <模型路径> <其他参数> &
# 等待服务就绪
python benchmark_serving.py \
    --backend openai --model <模型名> --base-url http://127.0.0.1:8000 \
    --dataset-name random \
    --random-input-len 1024 --random-output-len 128 \
    --num-prompts 200 --max-concurrency 16 \
    --save-result --result-dir ./results/baseline/
```

**方案 B：昇腾官方 ais_bench**：与昇腾硬件指标对齐更好，可用于交叉验证方案 A 的数值。

**方案 C：已有脚本迁移**：`/home/public/bench_base.py`、`bench_max_num_seqs.py` 等已有脚本可直接复用或改造。

### 5.5 采集纪律（重要）

1. **预热**：前 N 次请求（建议 ≥ 10 次或 ≥ 30 秒）不计入统计 —— 规避 DVFS 动态调频与 JIT/图捕获开销。
2. **稳态**：只测稳态，不测冷启动。
3. **重复**：每个配置点至少重复 3 次，报告中给出均值与标准差；方差 > 5% 视为无效数据，需排查环境干扰。
4. **环境锁定**：采集前
   ```bash
   echo performance | tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
   sysctl -w vm.swappiness=0
   ```
4. **记录温度**：`npu-smi info` 的 Temp 影响频率，温度差异过大时数据不可比。
5. **禁止并发实验**：同一时刻只跑一个实验，避免卡间资源争抢。

## 6. 阶段三：算子 Profiling 采集

### 6.1 目标

把端到端耗时**分解到算子粒度**，得到"哪些算子在吃时间"的量化事实。

### 6.2 三层采集粒度

| 层次 | 工具 | 粒度 | 回答什么问题 |
|------|------|------|--------------|
| **L1 模型级** | `torch_npu.profiler` / vLLM profiler | 算子调用序列 | 端到端时间都去哪了 |
| **L2 算子级** | `msprof` | 单算子 kernel 耗时 + pipe 占比 | 这个算子内部瓶颈在哪条流水 |
| **L3 微基准** | `msprof op` | 单算子独立跑 7 组 aic-metrics | 该 shape 下的算力/带宽利用率 |

**自顶向下**：先用 L1 定位热点 → 用 L2 分析热点内部 → 必要时用 L3 精确压测。

### 6.3 L1：模型级采集（最常用）

**方式一：vLLM 内建 profiler（推荐）**

```bash

# 启动服务后，通过 API 控制采集窗口
curl -X POST http://127.0.0.1:8000/start_profile
# ... 发送待分析的请求 ...
curl -X POST http://127.0.0.1:8000/stop_profile
```

**关键**：`start_profile` / `stop_profile` 之间**只包含要分析的请求**，且必须跳过 warmup。

**方式二：torch_npu.profiler 直接包裹**

```python
import torch, torch_npu

# 先跑若干步 warmup —— 这一步不能省，否则采到的是编译/图捕获开销
for _ in range(5):
    run_one_step()

with torch_npu.profiler.profile(
    activities=[
        torch_npu.profiler.ProfilerActivity.CPU,
        torch_npu.profiler.ProfilerActivity.NPU,
    ],
    schedule=torch_npu.profiler.schedule(wait=0, warmup=2, active=5, repeat=1),
    on_trace_ready=torch_npu.profiler.tensorboard_trace_handler("./profiles/run1"),
    profile_memory=True,
    with_stack=True,          # 需要 Python 调用栈时开启，开销较大
    experimental_config=torch_npu.profiler._ExperimentalConfig(
        aic_metrics=torch_npu.profiler.AiCMetrics.PipeUtilization  # 采集 pipe 占比
    ),
) as prof:
    for _ in range(8):
        run_one_step()
        prof.step()
```

- `op_statistic.csv` — 按算子类型聚合
- `trace_view.json` — MindStudio Insight / chrome://tracing 可视化

### 6.5 采集纪律（决定数据是否可用）

| 问题 | 正确做法 | 错误做法 |
|------|----------|----------|
| DVFS 降频 | `--warm-up` ≥ 3，先跑够再采 | 直接采第一次执行 |
| 采到编译开销 | 跳过前 N 步（图捕获/JIT 成本极高） | 从第 0 步开始采 |
| 把 profiling 数据当性能数据 | profiling 有 10%~3× 开销，**只用于占比分析** | 用 profiling 的耗时作为 TTFT |
| Prefill/Decode 混采 | **分开采集**：两者 kernel 构成完全不同 | 混在一起导致占比失真 |
| 多卡干扰 | 指定 device，或只采 rank 0 | 所有 rank 同时采 |
| 数据过大 | 限制 active 步数，只采稳态几 step | 全程采集导致 GB 级 json 无法分析 |

## 7. 阶段四：算子分析

### 7.1 目标

从 profiling 原始数据中提炼出**可执行的优化决策清单**：哪些算子该动、怎么动、优先级如何。

### 7.2 分析框架

对每个热点算子，回答三个问题：

```
     ┌─────────────────────────────────────────┐
     │  Q1: 耗时是否正常？                      │
     │      实测 vs 理论下限 vs 同类标杆          │
     └───────────────┬─────────────────────────┘
                     │ 不正常 ↓
     ┌───────────────┴─────────────────────────┐
     │  Q2: 异常原因是什么？                     │
     │      pipe 占比 / 搬运量 / 同步等待 / tiling │
     └───────────────┬─────────────────────────┘
                     │ 判定可优化 ↓
     ┌───────────────┴─────────────────────────┐
     │  Q3: 可融合吗？                          │
     │      数据依赖 + 中间结果落盘代价 + 收益估算  │
     └───────────────┬─────────────────────────┘
                     ▼
              优先级排序 → 进入阶段五
```

### 7.3 Q1：耗时是否正常 —— 判定方法

**方法一：理论下限对比（首选，客观）**

```python
# Memory-bound 算子的理论最短耗时（如 RMSNorm / Add / SiLU / Quant）
理论耗时 = 总访存量(Byte) / 实测HBM带宽(Byte/us)

# Compute-bound 算子的理论最短耗时（如 MatMul / Attention）
理论耗时 = FLOPs / 实测峰值算力(FLOPS/us)

# 计算效率
效率 = 理论耗时 / 实测耗时      # < 50% 说明有明显优化空间
```

> 实测带宽与算力必须**在本机压测得到**，不能直接引用规格书数据。用 msprof 对标杆算子（如 aclnn 的 `Add`、`MatMul`）采集即得。
> **注意**：小 shape 下搬运/启动开销占比高，实际达不到峰值属正常，需按 shape 规模分级判断。

**方法二：pipe 占比分析（定位瓶颈在哪条流水）**

| pipe | 含义 | 占比高说明 |
|------|------|-----------|
| `mte2` | GM → L1/UB 搬运 | Memory-bound，或搬运模式低效 |
| `mte3` | UB → GM 搬运 | 输出写回量大 |
| `vec` | 向量计算 | Compute-bound（Vector） |
| `cube` | 矩阵计算 | Compute-bound（Cube） |
| `fixpipe` | L0C → GM/UB | Cube 结果搬出 |
| `scalar` | 标量指令 | **tiling 计算过重或循环展开不足** |
| `mte1` | L1 → L0A/L0B | L1 到 Cube 搬运 |

**经验判据**：
- `mte2` > 60% → Memory-bound，优化方向是**减少搬运量或提升复用**
- `scalar` > 10% → tiling/地址计算拖累，优化方向是**循环展开、常量外提**
- `vec`/`cube` < 40% 且总耗时高 → 流水未打满，检查 **Double Buffer 是否生效**

**方法三：横向对比**

- 与**同类算子**对比：不同 shape 下同族算子的 scaling 曲线是否平滑，突变点即为异常
- 与**标杆实现**对比：CANN 内置算子、sglang 中的对应实现
- CANNBot 提供加速比对比模式（见 8.1 `ops-profiling --compare`）

**方法四：经验阈值（快速筛查）**

| 现象 | 判定 |
|------|------|
| 单 kernel 耗时 < 10 μs 且数量众多 | **小算子下发开销主导** → 考虑融合 |
| 算子耗时波动 > 20% | 可能受调度/邻居任务影响，需重采 |
| 同算子在 prefill/decode 下耗时占比差异巨大 | 正常（shape 差异），但说明需分场景优化 |

### 7.4 Q2：耗时异常 —— 典型模式与对策

| 异常模式 | 数据特征 | 根因 | 对策 |
|----------|----------|------|------|
| **小算子碎片化** | 大量 < 10 μs 的 kernel，数量占比 > 50%，耗时占比 < 10% | 下发开销 | 算子融合 / 图模式 / 算子批量下发 |
| **格式转换开销** | 出现 `TransData` / `ND2NZ` 等隐含算子 | 数据布局不匹配 | 上游算子直接输出目标格式；或用支持 ND 输入的算子 |
| **搬运占比过高** | `mte2` + `mte3` > 70% | 中间结果反复落 HBM | **融合**：把中间结果留在 UB |
| **流水未打满** | 单 pipe 占比高但总耗时更长 | 未开 Double Buffer / 同步点过多 | 检查 `TQue` depth、异步流水 |
| **tiling 尾块浪费** | 大 shape 反而比小 shape 效率低 | 尾块占比高 / 切分不均 | 重设计 tiling，多核均衡 |
| **scalar 拖累** | `scalar` 占比异常 | 地址计算在循环内 | 循环展开、指针自增 |
| **同步等待** | kernel 之间有空洞（trace 可见） | stream sync / 依赖等待 | 多流并行、减少同步点 |
| **未走图模式** | eager 下逐个下发 | ACLGraph 未覆盖该 shape | 扩展图捕获的 batch 分档 |

### 7.5 Q3：可融合算子识别

**融合的收益模型**：

```
融合收益 ≈ 节省的 HBM 读写量 / HBM带宽
         = (中间张量元素数 × dtype字节 × 2) / 带宽     # ×2 = 省一次写 + 一次读
```

若节省的时间 > 融合后 kernel 的额外开销，则融合正收益。

**可融合判定规则：**

| 判据 | 说明 | 权重 |
|------|------|------|
| **数据依赖** | 生产者-消费者关系，且中间结果**只有一个消费者** | 必要 |
| **中间结果落盘** | 中间张量必须写回 HBM 再读出 | 高 |
| **逐元素性质** | 链条上都是 elementwise / 规约类，无形状变换 | 高 |
| **形状兼容** | 各算子 shape/broadcast 规则可统一 tiling | 中 |
| **类型兼容** | 融合后 dtype 转换可内部完成 | 中 |

**大模型中的高价值融合场景（重点排查）：**

| 场景 | 典型链条 | 收益点 | 备注 |
|------|----------|--------|------|
| **归一化 + 量化** | RMSNorm → Quant (Cast to int8) | 省 2 次 HBM 往返 | W8A8 场景必查 |
| **残差 + 归一化** | Add(residual) → RMSNorm | 省中间张量 | 每层都有，收益 ×层数 |
| **激活 + 门控** | SiLU/GELU → Mul (SwiGLU) | 逐元素串联 | MoE FFN 必经 |
| **RoPE 系** | QK Norm → RoPE → Scatter | 多个小算子串联 | 长序列下占比上升 |
| **MoE 门控** | Gating → Softmax → TopK → Scatter | 全是小算子，下发开销主导 | MoE 模型重点 |
| **MoE 专家计算** | 多个小 MatMul（按专家分组） | 可合并为大 batch GEMM | 看分组策略 |
| **Attention 融合** | QK^T → Softmax → PV | FlashAttention 化 | 优先查是否已用 FIA |
| **MLA absorb** | KV 压缩/解压链路 | DeepSeek 特有 | 查是否已走 absorb 路径 |
| **量化矩阵乘** | Dequant → MatMul | Ascend 有专用融合算子 | 查 `npu_quant_matmul` 类接口 |
| **KV Cache 更新** | Cast → Reshape → Copy | 逐元素 + 搬运 | decode 阶段高频 |

**先查后造（顺序不能反）：**

1. **图模式是否已自动融合？** —— 开启 ACLGraph 后重采一次 profiling，对比算子数量。
2. **CANN 融合算子库是否已有？** —— 查 `torch_npu` 的 `npu_*` 融合接口（如 `npu_rms_norm`、`npu_apply_rotary_pos_emb`、`npu_fusion_attention`），已有则直接替换。
3. **sglang / 其他框架是否已有实现？** —— `/home/zhujianwei/sglang` 中可能已有可参考 kernel。
4. 以上都没有 → **才进入阶段五自研**。

> 自研融合算子的成本远高于替换为已有接口。**前 3 步能解决 80% 的问题。**

### 7.6 优先级排序

对候选清单排序，评分公式：

```
优先级 = (耗时占比 × 预期收益系数) / 实施难度系数

耗时占比     : profiling 实测，0~1
预期收益系数 : 融合=0.6(省2次搬运)~0.9；替换已有接口=0.9；算法重写=0.5
实施难度系数 : 替换已有接口=1；简单逐元素融合=2；复杂融合=4；算法重写=6
```

**决策矩阵：**

| | 高耗时占比 | 低耗时占比 |
|---|---|---|
| **易实施** | 🔥 **立即做** | ✅ 顺手做 |
| **难实施** | 📋 排期做（需评估 ROI） | ❌ **不做** |

| **3. 方案设计** | Tiling + 流水 | UB/L1 切分、核间切分、Double Buffer、数据类型 | `ascendc-tiling-design`、`npu-arch`、`ascendc-performance-best-practices` |
| **4. 代码实现** | Kernel + Host | AscendC kernel、tiling 函数、host 侧封装 | `ops-direct-invoke` |
| **5. 精度验证** | 对齐 golden | numpy/torch 参考实现对比，误差达标 | `ascendc-precision-debug`、`ops-precision-standard` |
| **6. 性能调优** | 采集 → 分析 → 迭代 | msprof 采集 pipe 占比，针对性优化 | `ops-profiling`、`ops-perf-optimize` |

> **顺序不可颠倒**：精度未通过就调性能，等于在错误的实现上做优化。

### 8.4 AscendC 性能关键点（速查）

**存储层次**

```
GM (HBM, 全局)  ──mte2──▶  L1 / UB  ──mte1──▶  L0A/L0B  ──cube──▶  L0C
     ▲                                                              │
     └──────────────────── fixpipe ─────────────────────────────────┘
```

| 层级 | 容量量级 | 用途 |
|------|----------|------|
| GM (HBM) | 数十 GB | 输入输出、中间结果 |
| L1 | 数百 KB ~ MB | Cube 输入缓存 |
| L0A/L0B/L0C | 数十~数百 KB | Cube 专用 |
| UB | 数十~256 KB | Vector 计算与搬运中转 |

**优化要点**

1. **减少 GM 往返是第一优先级** —— 融合的本质就是把中间结果留在 UB。
2. **Double Buffer 必须显式开启** —— `TQue` 的 `depth ≥ 2`，让搬运与计算重叠，否则 mte2 和 vec/cube 串行。
3. **Tiling 要匹配 UB 容量** —— 一次处理的数据不得超过 UB；同时兼顾多核负载均衡，避免尾块拖尾。
4. **减小 scalar 开销** —— 地址计算移出内层循环，用指针自增；循环适当展开。
5. **对齐访问** —— 尽量 32B 对齐，非对齐访问会显著降带宽。
6. **dtype 选择** —— Vector 计算 fp16/bf16 吞吐高于 fp32；量化场景用 int8 可进一步提速。
7. **同步最小化** —— 减少 `SyncAll` 等全核同步次数。
8. **核间切分** —— 充分利用 24 个 AI Core；小 shape 下核数开太多反而因调度开销变慢。

**融合算子设计要点**

- 融合后 UB 占用会叠加，需重新核算 tiling（这是融合最常见的失败原因）。
- 融合链越长，寄存器/UB 压力越大，通常 **2~4 个算子融为一段**收益最佳，过长反而劣化。
- 融合后 dtype 转换点变化，注意精度累积误差。

### 9.3 L2：模型级验证

**数值一致性（融合/替换算子的关键验证）**

```python
# 在模型中间层 dump tensor，与未优化版本对比
def compare(name, a, b):
    cos = torch.nn.functional.cosine_similarity(
        a.flatten().float(), b.flatten().float(), dim=0)
    rel = (a.float() - b.float()).norm() / (b.float().norm() + 1e-9)
    print(f"{name}: cosine={cos.item():.6f} rel_err={rel.item():.3e}")
    assert cos > 0.99, f"{name} 余弦相似度不达标"
```

**端到端精度**：跑评测集（如 MMLU / GSM8K / C-Eval），分数下降 > 0.5% 视为不通过。

**端到端性能**：复用阶段二的测试矩阵与脚本，与基线逐点对比：

```
改进率 = (基线值 - 优化后值) / 基线值 × 100%
```

## 12. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|------|------|------|------|
| **soc_version 判断错误** | 编译出的算子静默劣化 | 中 | 阶段 0 用最小算子实测确认；对比不同 soc 编译产物的性能 |
| **vLLM-Ascend 版本不配套** | 直接无法启动 | 中 | 严格查官方版本配套表；用已验证过的组合 |
| **自研融合算子反而变慢** | 浪费工期 | 中 | 先估算收益模型（7.5）；小步验证，单算子先测再集成 |
| **融合后精度不达标** | 需回退 | 中 | 保留 fp32 累加路径；中间结果做精度对比；分步融合 |
| **图模式不支持自定义算子** | 融合收益无法在端到端体现 | 中 | 优先走 `ops-registry-invoke` 注册路径 |
| **UB 溢出导致融合失败** | 编译/运行错误 | 高 | 融合前重新核算 UB 预算；控制在 2~4 个算子一段 |
| **优化收益被其他因素淹没** | 无法归因 | 中 | 严格单变量；每次改动独立 commit + 独立基线对比 |
| **硬件资源被占用/邻居干扰** | 数据不可比 | 高 | 实验前 `npu-smi` 检查；记录温度与占用；固定实验时段 |
| **profiling 开销误导优化方向** | 优化了错误目标 | 中 | 只用 profiling 看占比，不用它测绝对性能 |
| **框架补丁难以维护** | 升级即失效 | 中 | 优先用官方融合接口；必须打补丁时记录 patch 与版本绑定关系 |
