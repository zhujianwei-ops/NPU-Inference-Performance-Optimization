一、结论摘要

  1. 耗时高度集中：MatMulV2（55.4%）+ Transpose（20.0%）占设备时间约 3/4，其余 1000+ 种算子合计不到 25%。
  2. 最异常的是“KV/状态缓存索引链”：754 个 kernel 花掉 81.5 ms（23.6%），其中两次 5 维张量转置各 16.09 ms，是整份 profile 最慢的单个 kernel，属布局不匹配导致的整块拷贝，投入产出比最高。
  3. 两卡通信严重不对称：rank1(device7) 的通信 kernel 均值 1529 us、合计 1507.9 ms（占其设备时间 45%），rank0 同类算子均值仅 10.2 us，相差 150 倍，必须排查。
  4. 算子实现本身大多健康：逐元素类单次 1~7 us 且方差极小；GDN 线性注意力主链 8~48 us 很稳定；大矩阵乘 cube 利用率 74.5%~95.9%，属正常水平。
  5. 收益主要来自“融合 + 减数量”：1095 种算子里 1039 种均值不足 20 us，11417 个小 kernel 合计只占 57.6 ms 设备时间，却带来 3302 次 host 发射（约 157 ms）与大量流上排队（Cast 一项累计等待 182.6 ms）。
  6. host 侧最大单点：aclnnNonzeroV2 单次 19.6~35.9 ms（rank0 共 124.8 ms、rank1 共 160.2 ms），来自 hybrid linear attention 后端每步的 torch.nonzero。
数据可信度说明（重要）
1）本次采集 with_stack=True，产生 178.5 万个 python_function 事件（trace_view.json 达 708 MB / 641 MB），host 侧耗时被严重放大；本报告结论以设备侧 kernel 数据为准，host 数值只做横向比较。
2）采集日志出现 Get step range failed, the step node list is empty：profiler 未识别 step 边界，因此 step_trace_time.csv 与 Kernel/Operator View 的“按 step”指标是整个会话的聚合值，不能当单步耗时用。
3）10.85 s 窗口内设备只在 0~2.2 s 真正跑模型（2 次 step[EXTEND bs=1 toks=1] + 6 次 step[TARGET_VERIFY bs=1]），其余约 8.6 s 是 prefill delayer 的空转协商循环（每轮 all_gather + broadcast）。统计样本只有 2 个 prefill + 6 个 verify 迭代。
4）rank1 的 kernel_details.csv / TASK 表把通信条目（AivKernel、hcom_allReduce__503_*）计入通信任务，总量 3.34 s 与 op_statistic.csv 的 0.326 s 不一致；跨卡比较请以 op_statistic.csv 或本报告 rank0 表为准。
5）建议下次用 torch_npu.profiler 的 schedule + profiler.step() 显式打点并关闭 with_stack，否则拿不到单步指标。

三、哪些算子耗时正常、哪些不正常

判定口径

① 单次耗时与同规模算子/理论带宽是否匹配；② 长尾（最大值相对 P50 的倍数）；③ PMU：cube 利用率、AIC/AIV 各通路（MAC/VEC/MTE/SCALAR）占比、icache miss；④ 是否单核（Block Num=1）搬运大块数据；⑤ 跨卡是否对称；⑥ host API 单次是否超过 10 ms。

✅ 正常（实现健康，暂不需改）

算子依据
● 大 shape MatMulV2（N=17408/8704/8192/124160，K=5120）cube 利用率 74.5%~95.9%，与 910B bf16 理论水平相符；单次耗时随 N 线性增长，无异常长尾
● SwiGlu / Sigmoid / Mul / Add / LayerNorm / RMSNorm 等逐元素算子单次 1~7 us，P99/均值 < 2.5，分布集中，属于正常的访存型小算子
● GDN 线性注意力主链（recurrent_gated_delta_rule / causal_conv1d / gdn_gating / solve_tril）单次 8~48 us 且方差极小（recurrent_gated_delta_rule 288 次全部落在 22~27 us），实现健康
● FusedInferAttentionScore、split_qkvgate_gemma_rmsnorm_rope、SwiGlu 等已融合算子单次 5~23 us，已经具备融合形态，只是每层调用次数多
● Slice / ConcatD / Fill / OnesLike 等搬运类算子（单次代价）单次 1.3~5.5 us，本身不慢；问题在数量（4627 个 kernel 合计 11.0 ms）与 launch 开销

七、下一步建议

  1. 重采一份可用的 trace：关闭 with_stack，用 schedule(wait=0, warmup=1, active=N) + 每步 profiler.step()，并跑真实并发（而不是 bs=1 的 2 个 prefill + 6 个 verify），否则 step 指标与统计分布都不可用。
  2. 先做 P0/P1 四项：状态缓存布局、两卡通信不对称、nonzero、权重访存，这四项覆盖了当前 profile 里绝大部分可回收时间。
  3. 融合算子按“先大后小”落地：先做 KV/状态缓存写入的“转置 + 索引写入”融合（一次就能拿回 ~60 ms 量级），再做 GDN 与 RMSNorm 链的小算子融合。
  4. 建立回归基线：用 op_statistic.csv 的总耗时与 kernel 数作为基线（本次 345.6 ms / 14602 个 kernel），每次改动后对比这两个数即可判断收益。
